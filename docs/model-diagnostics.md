# Diagnose an AI migration before writing

Load the selected model, then choose a migration target. Each original batch of up to five Pokémon gets one generation and at most two corrections. Python validates every parsed attempt against SQLite through `/api/validate-batch`; only validated AI records reach the unchanged final `/api/migrate` request, which independently validates the complete migration before writing.

The main interface now defaults to **Llama-3.2-3B-Instruct-q4f32_1-MLC (recommended)** on WebLLM **0.2.87**, reflecting actual isolated single-record results, not a full-data guarantee. Qwen alternatives remain selectable. Every inference awaits `resetChat()`, then requests nonstream JSON with an explicit JSON-stringified structural schema. No source-valued `const` or enum forces a correct-looking response; all records must still be generated by the model and verified by Python. This uses the same runtime/model/schema combination as the successful isolated report.

Before the final request, validated AI rows are sorted by ID and relational types by Pokémon ID and slot; MongoDB embedded types are sorted by slot. This reconciles order-independent batch validation with the existing final validators. No fields or values are added, removed, or replaced.

## When migration stops

### Start with a no-write pilot

After loading a model, set **Pilot starting Pokémon ID** (default `1`) and use **Test one Pokémon for PostgreSQL/MongoDB/MariaDB (no writes)**. For the observed name-preservation failure, select `10` (Caterpie). Then use **Test up to five Pokémon (no writes)** at ID `1` and ID `6`: it selects the chosen source record plus up to four following records, not all 151, and includes every matching relation. Near the source end it uses fewer records without inventing padding. Invalid or unknown IDs stop without generation. Neither pilot calls `/api/migrate` or opens a destination tab. Passing proves only the selected record set/model/target validation, not a complete migration or destination connection. Diagnostics identify `pilot` or `batch-pilot` and runtime `0.2.87`, retaining selected IDs per attempt. Full migration buttons remain separate and unchanged in scope. Bounded recovery can run within a multi-record pilot using the same validation gates described below; it still never writes.

The prompt describes field types without example record values. Sprite URLs must be copied verbatim; null is valid only when present in the source. Validation feedback includes bounded expected source values and missing relation records so the model can correct its own output. These are diagnostic messages, not replacement migration records.

The root structure is explicitly `{"pokemon":[],"pokemon_types":[]}` for SQL targets and `{"pokemon":[]}` for MongoDB. These are templates to fill, not valid empty answers. Array fields remain arrays even for one record. Structural feedback uses JSON object/array terminology and identifies the failing path; the server does not automatically wrap or repair model output.

MongoDB prompts explicitly require renaming source `id` to `_id`, matching every relation by `pokemon_id`, embedding it under the document's `types` array, and renaming `type_name` to `name` while retaining `slot`. Neither `id` nor a separate `pokemon_types` array belongs in the MongoDB output. These rules are retained in every correction. The user input stays in the original relational format: the model, not browser or Python fallback code, performs this transformation.

The status identifies the target, batch number, IDs, and reason. Malformed JSON, incomplete records, content errors, and `finish_reason: length` consume the same three-attempt budget. A length-limited response is rejected even when it parses. Each correction keeps the original source-only JSON user input unchanged. The system instruction carries bounded validation details, explicitly marked as data, and repeats the same target output contract. No competing JSON request envelope or rejected assistant answer is provided. This changes request messages, not a guarantee that runtime inference state is reset. No fields are filled from source data, no JSON tokens are invented, and batches are not recursively split.

Network, generation-service, and validation-protocol failures stop immediately. Writes are never automatically retried. There are no checkpoints or resumable writes in this phase. After investigating a failed run, the user may explicitly start another migration.

### Common SQL generation and selective record recovery

PostgreSQL and MariaDB now use identical relational generation instructions for the same input. The chosen destination still controls validation, writing, and readback; only generation shares a contract.

After three rejected attempts on a multi-record batch, one bounded recovery pass is permitted if the last parsed response has unambiguous source IDs and partitionable relations. Truncated, malformed, extra-ID, duplicate-ID, or ambiguous relation structures stop instead. Python validates each candidate record with all its relations independently. Approved AI records are retained unchanged; only rejected records are requested again from the model, at most three times each. Single-record recovery cannot recursively start another recovery pass. A five-record batch therefore permits at most 18 generation calls (three original plus up to three per record), not unlimited retries. Recovery attempts have diagnostic `phase: "record-recovery"`.

MongoDB alone permits that last candidate to contain fewer documents than requested, including an empty document array. Present documents must still have unique, expected `_id` values and unambiguous type-slot identities. Python validates each present document before retaining it; omitted IDs produce an empty singleton candidate that validation rejects, then the model is asked to generate that specific document from the original source. No missing document or field is copied into the result by browser/Python code. The combined complete batch must pass validation again. SQL targets retain the original requirement that recovery candidates contain all requested record identities; their prompts, schemas and write paths are unchanged.

The merged batch must pass Python batch validation again. Complete output still passes final full-source validation before any destination write. No source values are substituted into AI output, and a persistently wrong name still stops the run. Retained records live only in memory for this run; this is not cross-run checkpointing. Passing a singleton pilot does not guarantee recovery of a complete migration.

## Download local diagnostics

Use **Download migration diagnostics (JSON)** beside the migration status. The native button is keyboard accessible and becomes enabled after the first attempt. Nothing is automatically saved to disk or exported to a logging service.

| Field | Retention |
|---|---|
| Attempts | Latest 100 in the current run; `dropped_attempts` counts evictions |
| Raw response | First 32,000 characters, with `raw_response_clipped` flag |
| Context | Selected model ID, target, batch number, source IDs, attempt number |
| Timing | Start time and duration including batch validation |
| Model metadata | Finish reason and available prompt/completion/total token counts |
| Validation errors | Up to 20 structured path/code/message entries, bounded per field |

Starting another run resets diagnostics; reloading the page discards them. Download uses a JSON Blob and revokes its temporary URL. Engine objects and credentials are not collected. Raw model output may contain source data or echoed sensitive text: inspect the downloaded file before sharing it. Ordinary source, batch-validation, and final migration requests still run as described above; diagnostics add no network export.

## Verification boundary

`tests/test_migration_browser.cjs` drives the public migration button with mocked DOM, model, and HTTP responses for PostgreSQL, MongoDB, and MariaDB. These deterministic tests verify orchestration, not WebGPU inference or real database writes. A real browser/model pilot and independent verification of untrusted model input (risk item 2) remain separate acceptance gates.
